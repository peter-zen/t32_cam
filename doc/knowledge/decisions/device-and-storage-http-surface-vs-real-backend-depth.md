# Device / Storage HTTP 表层与真实后端深度的分层决策

## 1. 决策主题

明确 `t32_cam` 当前为什么必须把下面两件事分开描述：
- HTTP 表层接口是否已经稳定存在
- 后端真实数据接线是否已经完成

如果把这两者混为一谈，就会错误得出：
- 路由有了 = 真实能力全有了
- 示例字段有了 = 已接真实硬件

这在 `device` / `storage` 域上尤其危险。

## 2. 当前事实基础

当前代码中：
- `device/info`、`device/sensors`、`storage/info`、`storage/format` 都已经有 V1 路由
- 但 handler 主要返回构造型 JSON
- 同时仓库里又确实存在部分底层能力：
  - `Disk::getInfo()`
  - MCU 电池相关读取

所以当前真实状态不是“完全没有能力”，也不是“已经全接好”，而是中间态。

## 3. 为什么要把“表层稳定”和“后端深度”分开

### 3.1 协议层对客户端是有价值的
即便当前值还是占位，固定的：
- 路径
- 方法
- JSON 结构
- 字段命名

仍然能让客户端先完成联调和解析逻辑。

### 3.2 但工程上不能把占位值伪装成真实数据
如果把当前 `battery=3700`、`total=32000` 之类写成实时采集值，会直接误导：
- APP 逻辑
- 测试判断
- 后续联调预期

### 3.3 camera 域已经证明“表层稳定 ≠ 深度一致”
当前 camera 域明显比 device / storage 深得多。
如果文档继续把四个域写成同成熟度，就是错误抽象。

## 4. 当前分层的收益

### 4.1 允许客户端先按稳定字段开发
可以先围绕稳定字段写：
- model parsing
- storage capacity UI
- battery UI

### 4.2 保持工程表述诚实
文档上明确“字段稳定但值未必真实接线”，能避免后续大量误会。

### 4.3 给后续补接线留下明确目标
后续补强时，目标就很清晰：
- 把 `Disk::getInfo()` 接进 `storage/info`
- 把 MCU / sensor 真实读取接进 `device/sensors`
- 把格式化真实流程接进 `storage/format`

## 5. 为什么现在不应把这几个域写得过满

原因很直接：
- 当前 handler 就是写死 JSON
- 没有看到真实调用链
- 如果文档还写成“已接硬件”，那就是文档撒谎，不是乐观表达

## 6. 决策结论

当前仓库应继续坚持以下表述边界：
1. `device` / `storage` 的 HTTP 表层已稳定
2. 后端真实接线仍然偏浅
3. 底层能力线索已存在，但尚未完整接入
4. 在真实接线补齐前，不把这些域描述成与 camera 域同成熟度

## 7. 何时需要重新评估

出现以下情况时，应重新评估并改写这组文档：
- `Disk::getInfo()` 已正式接入 `storage/info`
- `device/sensors` 已改为真实电池/存储/环境数据来源
- `storage/format` 已接入真实后台任务与状态观测
- event / mDNS / HTTP 已开始暴露 storage/device 状态变化

在那之前，继续保持“表层稳定、后端偏浅”的口径是必要的。
