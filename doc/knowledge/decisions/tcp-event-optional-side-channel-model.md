# TCP Event 作为可选旁路通知通道的决策

## 1. 决策主题

明确 `t32_cam` 当前为什么把 TCP Event 定位为：
- HTTP 控制面的旁路通知通道
- `CMD_MOBILE` 中的可选增强能力
- 不影响主业务结果的单客户端、无重放、无 ACK 首版模型

而不是：
- 主控制通道
- 必须成功才能进入主链路的硬前置服务
- 支持多客户端和可靠投递的复杂消息系统

## 2. 当前事实基础

当前代码表明：
- `TcpEventService` 已独立成模块
- `CMD_MOBILE` 中会尝试启动它
- 启动失败只打印 warning，不阻断 HTTP / RTSP 主链路
- `PhotoJobManager` 已通过它发送异步拍照完成/失败事件

这说明当前设计的核心语义已经落在代码里。

## 3. 为什么不是主控制通道

把 TCP Event 作为主控制通道是错误选择。

原因：
1. 当前系统已有 HTTP API 作为控制面
2. Event 的职责天然是“设备主动通知”，不是接收命令
3. 如果让 APP 同时在 event socket 上承载控制，会把请求/响应语义和通知语义混在一起
4. 对移动端和嵌入式端都会增加状态复杂度

因此当前坚持：
- HTTP 是控制面
- TCP Event 是通知面

这个分工是对的。

## 4. 为什么启动失败不阻断主链路

当前代码中 TCP Event 启动失败只记 warning，这是合理的。

原因：
- 设备控制和基础预览能力仍依赖 HTTP / RTSP
- 没有 event 通道，APP 仍可通过轮询继续工作
- 如果让 event server 失败就直接中断主链路，会把“增强体验能力”错误升级为“基础可用性前置条件”

这和 mDNS 不同。

mDNS 失败时，设备连被发现都可能做不到；而 TCP Event 失败时，控制面仍可工作。

## 5. 为什么首版采用单客户端模型

当前 `TcpEventService` 只保留一个 `clientFd_`，新连接替换旧连接。

这不是偷懒，而是当前阶段更合理的取舍。

原因：
- APP 侧主使用场景通常只有一个前台控制端
- 多客户端广播会引入：
  - fan-out 发送
  - 各客户端写失败隔离
  - 队列回压处理
  - 连接状态管理复杂度
- 当前真正有价值的是先跑通一条稳定事件通道，而不是先做通用 pub-sub 系统

## 6. 为什么不做 ACK / 重传 / 补发

当前没有：
- ACK
- 重传
- 离线缓存
- 断线补发

这是合理的首版边界，不是缺乏思考。

原因：
1. 事件当前主要承担“体验增强”和异步完成通知
2. 真正的权威状态仍可通过 HTTP 查询
3. 一旦引入 ACK / 重传 / replay，就会带来：
   - 持久化或内存队列
   - 去重
   - session 语义
   - 客户端恢复点协商
4. 这对当前仓库阶段来说明显过重

因此当前模型本质上是：
- best effort event side channel

## 7. 为什么现在值得保留这个旁路

即便它不是可靠消息总线，当前仍然有明确价值：
- 拍照异步任务完成时，不必让 APP 高频轮询
- 后续 storage / power / camera 状态变化有统一输出面
- 给未来更丰富的异步接口留出结构位置

也就是说，它不是“多余功能”，而是合理的渐进式能力底座。

## 8. 当前模型的代价

### 8.1 易丢事件
无客户端、断线、写失败都会丢事件。

### 8.2 无法多端同时订阅
单客户端替换意味着：
- 调试工具与正式 APP 同时连接时会相互踢掉

### 8.3 外部发现还不够完整
当前代码不能证明：
- `event_port` 已通过 HTTP / mDNS 对外完整暴露

这意味着 APP 侧接入便利性还不够强。

## 9. 决策结论

当前仓库应继续坚持以下模型：
1. TCP Event 是 HTTP 控制面的可选旁路通知通道
2. 在 `CMD_MOBILE` 中作为增强能力尝试启动
3. 启动失败不阻断主链路
4. 保持单客户端、无 ACK、无 replay 的轻量首版模型
5. 真实状态仍以 HTTP 查询为最终兜底

在没有明确需求前，不建议：
- 把它升级成主控制通道
- 强行做可靠消息系统
- 一开始就扩成多客户端订阅中心

## 10. 何时需要重新评估

出现以下需求时，应重新评估当前决策：
- 多终端同时订阅成为刚需
- APP 强依赖事件而不能容忍丢失
- 需要断线恢复和历史事件补拉
- 需要通过 mDNS / HTTP 明确暴露 `event_port`
- storage / power / workmode 等大量异步事件开始接入

在这些需求明确之前，当前模型是合理的工程折中。
