# t32_cam 仓库知识库说明

## 1. 目的

本目录 `doc/knowledge/` 是 t32_cam 仓库内的项目级权威知识层，用于沉淀：
- 项目概览与当前工作集
- 规格说明 (specs)
- 架构/方案决策 (decisions)
- 缺陷与根因分析 (bugs)
- 操作流程与调试手册 (playbooks)
- 外部参考与上下游约束 (refs)
- 待整理笔记 (inbox)
- 阶段性评审与治理记录 (reviews)

如果这里的内容与 `~/hermes_knowledge` 中该项目的索引摘要冲突，以本仓库内 `doc/knowledge/` 为准。

## 2. 默认阅读顺序

新会话或新代理进入本项目时，默认按以下顺序读取：
1. `overview.md`
2. `working-set.md`
3. 与当前任务最相关的 1~3 篇文档
4. 再按需要读取源码、脚本和测试

不要一开始就通读整个 `doc/` 目录；那会制造噪音。

## 3. 目录说明

- `overview.md`
  - 项目目标、运行形态、构建模式、主要子系统、当前阶段
- `working-set.md`
  - 当前重点、任务入口、关键代码路径、近期风险、推荐先读项
- `todo.md`
  - 结构化记录 now / next / later / blocked
- `specs/`
  - 行为规格、接口契约、输入输出、验收条件
- `decisions/`
  - 架构选择、替代方案比较、决策原因与后果
- `bugs/`
  - 现象、复现、根因、修复、回归风险
- `playbooks/`
  - 可重复执行的流程，例如环境准备、仿真构建、联调、发布、排障
- `refs/`
  - 外部资料摘要、第三方依赖说明、历史文档映射
- `inbox/`
  - 尚未定型的草稿、线索、临时记录；稳定后应提升到正式目录
- `reviews/`
  - 知识治理、阶段评审、迁移记录、校准记录

## 4. 归档规则

- 与项目事实直接相关的内容，优先放在本目录，而不是外部知识库。
- `doc/` 下原有的历史文档可继续保留，但后续应逐步：
  - 将仍然有效且需要长期维护的内容迁入 `doc/knowledge/`
  - 或在 `doc/knowledge/refs/` / `reviews/` 中建立映射与说明
- 当不确定一篇新文档归属时，先放入 `inbox/`，确认稳定后再提升。

## 5. 与历史 `doc/` 目录的关系

当前仓库已经存在大量历史文档，主要散落在：
- `doc/analysis/`
- `doc/design/`
- `doc/solution/`
- `doc/job/`
- `doc/reference/`
- `doc/review/`
- 若干顶层报告/方案文档

这些历史文档暂不强制搬迁；本轮先建立统一入口与分类规则，使后续新增/治理工作有明确落点。

## 6. 后续维护原则

- 新增项目知识，默认写入 `doc/knowledge/`
- 项目级事实以 `doc/knowledge/` 为唯一长期权威入口
- 如果某篇历史文档已过时，不要继续在旧位置追加维护；应改为在 `doc/knowledge/` 中写新的权威版本，并在需要时补充映射说明
